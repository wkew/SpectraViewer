# Synthetic performance prototype

A runnable first experiment: synthesize a transient, load its binary data,
apodize, Fourier transform, release intermediates, write a file-backed magnitude
spectrum, and review up to 200 scaled-copy traces with a multiresolution display.

**This isolates NumPy/SciPy and Qt costs. It does not yet benchmark CoreMS, import
Bruker data, or implement a validated instrument calibration.**

## Run the demo

Requires Python 3.10+ and a desktop environment for the interactive window.
Tested here on Python 3.12/Linux; Windows/macOS have not been tested.

```bash
git clone https://github.com/wkew/SpectraViewer.git
cd SpectraViewer
python -m venv .venv
# Activate: Windows PowerShell -> .venv\Scripts\Activate.ps1
# Activate: macOS/Linux -> source .venv/bin/activate
python -m pip install -r requirements.txt
python prepare_demo.py
python viewer.py
```

`prepare_demo.py` creates and processes a **1M-sample** synthetic transient locally.
It reuses a completed demo on subsequent runs. Generated data are ignored by git.
The reported large-data measurements use a separate **64M-sample** dataset;
large binaries are regenerated by the commands below rather than bundled.

Viewer controls: wheel zoom, mouse drag pan, Full view, Strongest peak,
1–200 traces, overlay/stack, and PNG export. The status bar reports data
preparation + plot submission latency, **excluding painting**. The plot displays
exact samples when zoomed sufficiently far in. The first version prepares views
synchronously with a short debounce; large processing runs use the separate CLI.

## Reproduce the large test

```bash
python check_correctness.py
python run_suite.py --points 67108864 --repeats 3 --pad-factors 1 2 --out local_run
python viewer.py local_run/pad1_run1
```

Use a fresh output directory. About 8 GiB available RAM and a few GiB of free
disk are sensible for this suite; the measured 2x-padded worker peaked near
4 GiB here. The suite runs fresh processing processes sequentially, keeps one
profile per padding factor and all JSON timing reports, and deletes its redundant
repeat profiles. The OS page cache is **not** cleared. The display benchmark uses
Qt's offscreen CPU painting and requires no visible desktop.

For a smaller run:

```bash
python run_suite.py --points 1048576 --repeats 1 --pad-factors 1 --out small_run
```

Or run individual stages:

```bash
python benchmark.py generate raw64 --points 67108864 --tones 48 --seed 42
python benchmark.py process raw64 spectrum64
python benchmark.py process raw64 spectrum64_zf --pad-factor 2
python viewer.py spectrum64 --benchmark --output render_results --frames 12
python viewer.py spectrum64
```

`--pad-factor 2` means the FFT has twice the original transient length, not two
successive doubling operations. `--pad-factor 4` is available but was not measured.
The generator refuses to overwrite raw data and the processor refuses to
overwrite an existing profile.

## What is measured

| Stage | Implementation |
|---|---|
| Synthetic data | Chunked direct summation of 48 random-frequency, random-phase damped sine waves; log-uniform amplitudes; Gaussian noise; int32 quantization |
| Binary read | Little-endian int32 `numpy.fromfile`, forced full read |
| Preparation | Float64 conversion; int32 released; symmetric Hann window computed in bounded chunks and multiplied in place |
| FFT | `scipy.fft.rfft`, float64/complex128, one worker; optional backend zero padding |
| Magnitude | Chunked absolute value into a float64 `.npy` memory map; complex output released |
| Calibration | Synthetic `m/z = A/f`, with `A=1e8`; frequency inferred from bin index; DC omitted |
| Display cache | 64-sample min/max blocks, then 4:1 hierarchy; original extrema indices preserved |
| View preparation | Read appropriate summary blocks or raw samples; compute only the required m/z values; handle partial edge blocks from raw data |
| Display | 1, 20, 200 separately prepared scaled copies; overlay and stack; full, region, exact-sample windows |
| Qt timing | Preparation, `setData`/range submission, and forced 1800×1000 QImage painting measured separately |

Mass mapping is lazy, so there is no full-length m/z array resident or written.
The min/max hierarchy is built in frequency-bin space; it is **not** exactly
one pair of extrema per screen pixel on the nonlinear mass axis. It preserves
block extrema, not every peak shape. Full-resolution samples remain authoritative.
The hierarchy is independent of calibration coefficients for this monotonic
mapping. A real calibration needs instrument-specific coefficients and validation.

## Interpretation and boundaries

- Numerical processing is real, including a real 64M FFT; no extrapolation from a small FFT.
- 200 traces are **scaled copies of one underlying profile**, with separate
  x/y arrays and separate plot objects. This tests preparation and rendering,
  not loading, processing, or caching 200 independent datasets. Shared OS pages
  make it an optimistic memory and I/O scenario.
- The synthetic spectrum has 48 isolated tones. Real environmental FTICR spectra
  can be far denser; their clutter and rendering cost may differ.
- Read speeds are OS-cache-influenced, not proven cold SSD/network-storage speeds.
- `.flush()` time does not guarantee all data are durably committed to hardware.
- Display figures are offscreen CPU render times, not measured monitor FPS,
  end-to-end mouse latency or GPU throughput. Each case has 12 timed updates after
  one warm-up; p95 is descriptive for this small sample, not a robust SLA.
- RSS is sampled every 5 ms, covering native buffers and resident mapped pages;
  short-lived peaks can be missed. OS high-water RSS is also recorded on Unix.
  `tracemalloc` alone would miss much of this workload.
- `del` removes references but does not guarantee that native allocators return
  memory to the OS. The suite uses fresh subprocesses to recover that memory
  between jobs. Backend zero padding and `overwrite_x=True` do not guarantee an
  in-place transform; measured peak RSS is more useful than array-size arithmetic.
- No CoreMS performance claim, vendor equivalence, formula annotation,
  recalibration fitting, peak picking, or isotope matching is implied.

## Files

- `benchmark.py`: synthesis, pipeline, cache, memory/timing instrumentation.
- `viewer.py`: interactive viewer and offscreen render benchmark.
- `run_suite.py`: sequential fresh-process repetitions and render test.
- `check_correctness.py`: numerical and display-cache checks against references.
- [`RESULTS.md`](../RESULTS.md): measured results and conclusions from this environment.
- `results/`: recorded JSON timing reports and correctness results.
  Running the display benchmark locally also produces preview PNGs.
- `prepare_demo.py`: generates the small local `demo/` dataset.
- `demo/`: generated data, excluded from git.

## Next useful experiment

Add a CoreMS adapter behind the same timing boundaries, compare output against
this baseline and Bruker on a real file, then run genuinely distinct spectra
from the lab's actual storage. Keep the renderer's compact-array interface.
If redraw remains the bottleneck, try batching traces into fewer drawing objects
and compare a GPU renderer before considering a Rust rewrite of the whole app.
